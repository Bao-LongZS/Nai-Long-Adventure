## 1. 本次评估结论

原计划的玩法、确定性架构、α 止损思路和 A1–A7 验收项整体可保留；以下问题已按开工标准裁定：

| 原问题 | 影响 | v2 裁定 |
|---|---|---|
| 工程、人天和角色动画预算混写；W1–W4 只给单值合计 27 天，另写 α 20/30 乐/悲但未说明单项换算 | 排期无法知道预算含不含美术，难以复核 WBS | 20–30 明确为 α 工程人天；另列 10.7–16.9 美术人天；各工作包给范围且能加总 |
| 2D 方向已冻结，但提出 69 帧/三朝向，又假设 α 动画 ≤3 天 | 既没有分层源稿，也没有产能样片，成本假设无法成立 | α 先交付 33 个唯一帧（侧面左右镜像）；按帧生产率做初估，W1 真实动作样片校准；69 帧作为后续扩展上限参考，不作为 α 承诺 |
| “环境资产复用”没有逐项核验，有“零新资产”和“角色另计”的口径摇摆 | P2/P3 资产/角色、贴花可能未经验证就进入预算 | P2/P3 均标为候选；P4 独立路径保留引用，不复制；以台账和实际视角/alpha/比例检查决定复用 |
| 计划称 W1 开工，但后续执行记录仍有中心标尺、阴影、深度排序、帧时间和动作方向未验收 | 容易把构建/脚本退出码误报成关卡通过 | 当前 W1 明确标记“进行中”；逐项记录 PASS/FAIL/未测，缺证据不放 W2 |
| 负责人只写“尚未指定”，验收 PC 缺失，菜单入口有书面批准门但 α 范围同时写必须有入口 | 无法分配任务且入口授权矛盾 | 以岗位责任分配，人员姓名/验收机需 G0 登记；无菜单批准时只能交内部地图测试，不可称正式菜单接入完成 |
| 62–101 人天被包装为完整 P4 工期，却未计 β/γ 美术 | 全量十章总预算不完整 | 62–101 仅为工程；β/γ 美术等 α 体验门通过后按正式角色/敌人/场景清单估算 |
| 性能条款同时写 α 16.7 ms、完整 P4 8 ms，但没有设备基线 | 通过条件不一致、无法比较 | α 用指定 PC 的 p95 ≤16.7 ms（60 fps）硬门；完整版 p95 ≤8 ms 为目标预算，W0 记录 PC 并在 β 前以实测决定是否冻结 |

## 2. 产品范围与技术冻结

P4 是独立地图、独立 Pawn/GameMode、独立存档槽的 PC 横屏单屏清版子模式；不参与 P1/P2/P3 进度链。菜单是否新增“模式条”入口仍按单独批准门执行。键位、1/60 定步长、固定透视机位、DataTable+CSV、FSM、命中/状态阶段顺序和战斗数值详情以工程计划与设计基线为准。

| 阶段 | 可玩交付 | 不在本阶段承诺 |
|---|---|---|
| α 竖切 | 3–5 分钟：一张沙盒竞技场、5 波/20 只敌人、奶丁/奶盾、奶桶队长简化两招、玩家走位/普攻/冲撞/防御/大笑、三张固定强化卡、死亡回本章重试 | 十章、完整 16 敌/4 Boss、进度存档、手机、未获批准的菜单入口、完整敌人/老板角色动画 |
| β 内容铺开 | α 决策继续后再扩 10 章、330 杂兵、4 Boss、完整卡池/字幕/进度与选关入口 | 不因完成 α 自动开始；需重新冻结资产清单和美术预算 |
| γ 收口 | 全章平衡、可读性、性能、回归、Windows 包和交付记录 | 不用未测的编辑器截图或单次试玩替代包内验收 |

**角色方向：2D 奶蛙立绘是战斗主体，3D 场地只提供纵深和落地感。**不换回 3D 主角，不使用 SkeletalMesh 作 α 运行时主角。用户给出的 `player.png` 是奶蛙身份/造型基准；`Big_Laugh.png` 是奶龙母体对照，不能把母体当奶蛙。P3 静态 PNG 只用于技术/笔触候选；不能当动作帧或已批准 P4 成品。

## 3. 责任岗位与计划分轨

| 工作包 | 主责岗位 | 验收参与岗位 | 责任边界 |
|---|---|---|---|
| 玩法参数、DataTable、模拟状态、固定步长、输入、战斗/AI/波次/Boss | Gameplay Engineer | QA + Designer | 维护唯一权威模拟状态、数据验证和状态 hash；不以表现层 Actor 作为玩法真源 |
| 笑场反制、波次节奏、预警/卡牌语义 | Game/Combat Designer | Gameplay Engineer + QA | 给出锁定参数及理由；确定性数据和错误状态用例齐全 |
| 角色 2D 帧、环境适配、UI 标记、图集/色板 | 2D Artist + Technical Artist | Designer + Gameplay Engineer | 交付源稿、atlas manifest、导入参数；不写伤害/答案逻辑 |
| 地图表现、脚底锚点、DepthY 排序、HUD 绑定 | Gameplay Engineer + TA | QA + Designer | 工程负责运行时与测量；美术负责资产质量和来源 |
| Windows 打包、设备性能、玩家形成性试玩 | QA/Build Owner | Designer + Engineer + 项目负责人 | 采集证据、记录缺陷并复测；样本结果只作方向信号 |
| 范围、样片风格和入口授权 | 项目负责人 | 各 owner | 2D 方向已确认；菜单改动另按既有批准条件处理 |

姓名与到岗比例尚未写进项目资料，因此计划先按**岗位 owner**分工，不捏造个人姓名或自然日排期。项目负责人在 W0 工作表登记具体执行人/替补人、验收 PC 和计划启动日后，才换算日历排程。

## 4. 预算与范围基线

| 口径 | 工程 | 美术 | 合计/状态 |
|---|---:|---:|---|
| α | 20–30 人天 | 10.7–16.9 人天 | **30.7–46.9 人天**（约 31–47）；美术独立核算 |
| β | 32–52 人天 | 待 α 后审计 | 只在 α 方向门通过后估 |
| γ | 10–19 人天 | 待 β 范围/缺陷清单 | 只在 β 资产与体验范围冻结后估 |
| P4 完整工程 | **62–101 人天** | 不含 β/γ 美术工作 | 不是全项目含美术总工期 |

1 人天 = 6 小时有效工作。α 工程估算包含 W1 已完成/进行中的 P4 骨架、数据和可视验证工作；当前未有可靠实际工时台账，不从估算中扣除“已做天数”。各阶段估算见[工程计划](P4_工程计划_v2.md)和[美术计划](P4_美术执行计划_v1.md)。

## 5. 阶段顺序、任务出口与止损

| 阶段 | 目标 | 通过门 | 失败处理 |
|---|---|---|---|
| G0/W1（当前） | 确认工程安全边界；完成相机/角色呈现/DataTable 技术样片；锁定 alpha 帧数与样片工时 | 中心深度尺、纵深尺、脚底基线通过；两静姿技术读取正确；软影/排序评审通过；p95 测量；一项真实动作样片通过且 art estimate 重算；CSV/DataTable 回读与实际重导入行为有证据；验收机/owner 留档 | 任一硬项缺证据仍记未通过；保留不冲突的纯数据/源码工作，不进入依赖 Editor/资产的 W2 |
| W2 | 运行时玩家动作、攻击/输入、模拟数值和灰盒战斗 | 走位、普攻、冲撞、防御、大笑都能实际使用；大笑对盾顶可打断、对撞墙易伤有一次明确收益；3–5 人试玩过止损门 | 方向不成立时最多 2 工程人天调参复测一次；仍失败则改机制/缩范围，不铺敌人波次 |
| W3 | 两敌类型、5 波/20 只敌人、HUD 和 DataTable 驱动 | 完整波次无 C++ 逐波特判；同 seed 两次结果一致；能读预警；场景占位与角色不遮挡 |
| W4 | 简化 Boss、三卡、死亡重试、包内 α 验收 | A1–A7 全项有 PASS/FAIL 证据；Windows 包连续三局零崩溃/软锁；未获菜单批准时验收文案只能写“内部灰盒” |
| α 体验决策 | 3–5 位玩家、每人 2 局的形成性评估 | 达到原 α 门中的主动走位/冲撞/防御选择、大笑反制理解和笑点观察阈值；不将小样本包装成统计结论 | 不过门则只改可读性/反馈或核心机制，最多一轮复测，再决定暂停或另立新范围；不自动开始 β |

完整玩法矩阵、seed/hash、P0/P1 缺陷定义沿用 α 竖切规格；本次已把 A6 视觉/性能门拆为“α 运行最低门”与“完整版目标预算”。所有截图/日志写入 `UE5/Records/p4_alpha/evidence/W1/` 或 `W2/`，每份证据标出 build/commit/PC/分辨率/seed/结果。
